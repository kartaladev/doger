# Design

## Context

See proposal.md for the motivation. Today's facts that shape the approach:

- `Start`, `RefreshWithContext` and `Scope.StartWithContext` share `runPipeline` (`root_start.go`). Every Starter goes through `startCandidate` → `startInstance`, both in the sequential loop and in `startStartersParallel`. Every kind-handler call (including the default `Runnable` handler, `runRunner`) goes through `callKindHandler` from `runStage`. These two functions are the only places where user start code runs, so they are the only places this change needs to touch.
- Both call user code inline, on the run's goroutine, with the Start-time context (`startCtx`, derived from the caller's ctx and cancelled by Shutdown with cause `ErrShutdown`). Both recover panics into errors.
- `startCandidate` marks a Starter started on a nil return (`root_start.go:818`), before the run's next `checkAbort`. So a Starter that returns nil after the ctx ended is still recorded as started. This change keeps that.
- Step failures are wrapped by `withAbortCause`, which appends "(start aborted: <cause>)" when the run ctx is done. `abortOutcome` in `finishStart` makes a Shutdown-aborted run match `ErrShutdown`, with each cause appearing once (spec "An aborted run matches ErrShutdown when the caller cancelled first").
- The run holds `pipelineMu` for its whole duration, so a stuck step also blocks every later Refresh and Scope.Start.
- Started and handled bookkeeping: `RootScope.started` and `handled`, guarded by `startedMu`. That is a leaf lock, "never held across user code" (`root_scope.go:152`). `forget` clears both maps when a shutdown removes a service. A shutdown marks its scope as closing under `lifecycleMu` before it removes services (`claimCandidates` relies on this). Discovery (`newStartCandidate`) reads `isStarted`/`isHandled` long before the step runs.
- Timing uses `InjectorOpts.Clock` (`withClockTimeout`, `Clock.AfterFunc`, `beginServiceOp`/`elapsed`). The health-check bound (`HealthCheckTimeout`, where 0 means `DefaultHealthReportCheckTimeout` and a negative value means no bound, plus `ErrHealthCheckTimeout`) is the precedent for naming, zero-value semantics and the error shape.
- Logging goes through `Scope.log` / `logEnabled` and is off unless `InjectorOpts.Logger` is set. Today every record is emitted on a caller-owned goroutine. Panics are logged by `Scope.logRecoveredPanic` (ERROR with the panic type, DEBUG with the value). The `RootScope` variant always logs the root scope.
- README Go blocks are pinned by `TestReadme_SnippetsCompiled`. `docs_snippets_test.go` pins only `migrating/migrating-from-samber-do.md` (`TestDocs_MigrationSnippetsCompiled`/`Run`).

## Goals / Non-Goals

**Goals:**
- One per-step guard used by both the Starter and the kind-handler call sites, so Start, Refresh, Scope.Start, sequential start and parallel start all behave the same.
- With zero configuration: no extra goroutine, no change in ordering, errors, panics or bookkeeping. The only addition is a timer that is armed only when a Warn-enabled Logger exists.
- User start code is never called twice at the same time within one container.
- Abandonment never leaves a goroutine that cannot exit once the user's call returns, and nothing on an unowned goroutine can crash the process.

**Non-Goals:**
- Bounding Shutdown-side hooks, remote subscription stop, or HealthScheduler stop. These are sweep findings, listed in the proposal for separate changes.
- Killing or interrupting user code. Go cannot do that; abandonment only stops waiting.
- A bound on providers (builds). Invocation takes no ctx, and builds are already abandoned by Shutdown.
- A whole-run deadline. The caller's ctx deadline already is one; with `StartTimeout` set, an ended context cancels the running step's context at once and the step is abandoned at its timeout at the latest (D4).
- A start-failure hook for child scopes, matching `HookContainerFailed`, and de-duplicating the "waiting for start" report errors of a root Shutdown over a child scope. Both predate this change and are listed as follow-ups in tasks.md.

## Decisions

**D1. One guard, `runStartStep`, wraps both call sites.** It takes the run ctx and a `startStep` (candidate, op `start`/`handle`, kind id) plus the call `func(ctx) error`. `startCandidate` passes `startInstance` and `runStage` passes `callKindHandler`. The per-service hooks stay outside the guard, on the run's goroutine (`onBeforeStart` before it, `onAfterStart` after it), so hook panic semantics are unchanged.
*Alternative:* separate logic in each site. Rejected because the two copies would drift, and parallel start would need a third.

**D2. The slow warning is a `Clock.AfterFunc` timer, armed only when it can log, and stopped when the run stops waiting.** At step begin, the threshold is resolved (0 → `DefaultSlowStartThreshold` = 10s, negative → off). The timer is armed only if `logEnabled(slog.LevelWarn)` holds, so a container without a Logger, or with a level above Warn, never calls `AfterFunc` (checked with a counting Clock). When the timer fires it emits the WARN record once, inside a `recover` that drops a handler panic (D8). The timer is stopped on the step's return, and, with `StartTimeout` set, inside `awaitStep` right after its wait (review F4: stopping it only when `runStartStep` returned let a timer that fired with the abandonment still log). With `StartTimeout` set, a threshold at or above it arms nothing: the abandonment reports the step, and the outcome no longer depends on which of two timers due at the same instant fires first. A step abandoned before the threshold therefore never warns; its end is reported by the late-outcome record instead. A stopped `time.AfterFunc` timer never creates a goroutine, so the timer cannot leak. If the step returns exactly as the timer fires, 0 or 1 record is emitted, never 2. The timer lives on the container Clock, as the clock spec requires, so on a consumer's fake clock it is one more armed timer per step while a Warn-enabled Logger is set, and it counts toward that clock's `BlockUntil`. The `Clock` and `SlowStartThreshold` godoc and `options.md` say so, and `SlowStartThreshold: -1` removes it (review F6).
*Alternatives:* a watcher goroutine per step (rejected: one goroutine per Starter for a log line). A `HookSlowStart` callback (deferred: it can be added later without breaking anything, and `Logger` already gives full control over the destination).

**D3. With `StartTimeout` ≤ 0, the call stays inline.** No goroutine and no select: the code path is the same as today, including the started bookkeeping, so the "Start waits for every step by default" scenarios and the existing suite pin the unchanged behaviour. The one difference: the call receives its own child of the run's context (`context.WithCancelCause`, no goroutine), registered for its scope (D12), so that a child scope Shutdown can cancel it without cancelling the whole run. It keeps the run context's lifetime unless its scope shuts down: it is not cancelled on return, and the run's context releases it when the run ends.

**D4. With `StartTimeout` > 0, the call runs in a goroutine and the run selects.** The step ctx is `context.WithCancelCause(runCtx)` plus a `Clock.AfterFunc(StartTimeout, …)` timer that cancels it with the internal cause `errStepTimedOut`. The callee receives it; the hooks keep the run ctx (spec "Per-service start hooks", modified). When the call returns in time, only the timer is stopped: the step ctx stays live until the run ctx ends, so it keeps the lifetime it has without the option (review F3). Its cancel function is called only at abandonment. Not calling it on a normal return leaks nothing, because the run ctx is always cancelled when the run returns (`finishStart`, `finishIncremental`), which releases the child. It reports no deadline: a step that returns in time keeps it past the timeout, so a reported deadline would be false. The call's goroutine records its outcome under the call's mutex and closes a `returned` channel, so it can always exit once the user call returns, even if nobody waits.
- *Only the timer abandons (review F1).* The run waits on `returned` or on a `timedOut` channel closed by the timer callback, never on `stepCtx.Done()`. The run's context ending cancels the step's context at once, since it is its parent; a step that honours it returns, and the run keeps waiting until the step returns or its timer fires. So a Start that honours its context is never abandoned while it unwinds, and root Shutdown, which waits for the run bounded by its own context (`waitForStart`), never runs that service's Shutdowner before its Start returned. A Shutdown bounded below `StartTimeout` stops waiting when its context ends and proceeds with that ended context, so it skips the services it reaches as shutdown-context specifies, exactly as without the option (triage A corrected the earlier claim that it runs the Shutdowner); the stuck step keeps running until its call returns, and the `StartTimeout` godoc says so.
- *The timeout is decided once (review F4).* The timer callback and the end of the call are ordered under the call's mutex. A callback that finds the call ended does nothing, so a step that returned in time keeps a live context. A callback that runs first marks the call timed out, registers the step as abandoned (D5), cancels the step ctx with `errStepTimedOut` and closes `timedOut`; the call's end, even one that comes before the run notices, is then its late outcome (D5). Registering the step in the callback, before the context is cancelled, guarantees that the late outcome always finds it registered.
- *After the wait.* A call that ended and was not timed out is handled as today (error → `*StartError` via `withAbortCause`, panic → error). A `runtime.Goexit` in user code still runs the deferred send, and is reported as a step error with panic type `runtime.Goexit`. Without `StartTimeout` the call runs inline (D3), where a Goexit ends the caller's goroutine, as before this change; the `StartTimeout` godoc states the difference (review F7). A timed-out call yields `libErrorf("%w after %s: %w", ErrStartTimeout, StartTimeout, context.DeadlineExceeded)`, wrapped by `newStartError`; `withAbortCause` appends the run's cause once if the run's context has ended meanwhile (review F5): "…: start timeout after 5s: context deadline exceeded (start aborted: context canceled)". A Shutdown-triggered abort still goes through `abortOutcome`, which finds the error already matching `ErrShutdown` and leaves it unchanged.
*Alternative:* always run in a goroutine. Rejected because it changes goroutine identity for user code with zero config (goroutine-local assumptions, stack traces), and D3 keeps the default byte-for-byte.

**D5. Abandoned bookkeeping: one atomic claim per step, and a guarded late mark.**
- *State:* `abandoned map[any]map[stepKey]struct{}`, keyed by service wrapper. `stepKey` is `start`, or the kind id for a handler. It lives next to `started`/`handled` under `startedMu`.
- *Claim (fixes the discovery-to-start window):* in `startCandidate` and `runStage`, before any hook (the hooks sit outside `runStartStep`), one `startedMu` critical section decides:
  - if the step is already recorded (started, or handled for that kind), skip it: return nil, with no hooks and no call;
  - if it is abandoned, skip it with no hooks, and keep `newStartError(op, …, libErrorf("%w: a previous call is still running", ErrStartTimeout))` as the run's pending error (review F2);
  - otherwise proceed.
  Discovery's early `isStarted`/`isHandled` stays as a cheap filter, but the claim is authoritative.
- *Skip, not stop (review F2):* the run keeps the set of services whose step it skipped as still running. A candidate that depends on one of them, directly or through others, is skipped too, with no hooks and no call; everything else is started. A service with a skipped step also has its later steps in the run skipped (for example its Starter after its own `StageBeforeStart` handler call was skipped), since a stage runs only after the earlier stages of its service. The run then returns its first failure if a step failed, and otherwise the pending error of the first still-running step it skipped. So one stuck step no longer blocks every later Refresh for services that do not need it.
- *Dependents across scopes (triage B, I3):* the dependency check does not stop at the run's own candidates. A candidate whose dependency, resolved through the dependency graph in its own or an ancestor scope, is a service with an abandoned call still running is skipped the same way, and reported with that step's error. So `tenant.Start()` treats a still-running root step like `root.Refresh()` does. The same consultation covers a dependent whose own step runs in an earlier pipeline stage than the still-running step (a Starter that depends on a still-running Runnable, or a `StageBeforeStart` component that depends on a still-running Starter): the run knows the abandoned state before its first stage, not only once it claims the still-running step (group 25 verification). An ancestor service that merely failed or never started keeps today's rule: Scope.Start does not start ancestors, and their dependents still start. Implementation (group 32): the `abandoned` set keeps each abandoned `startStep`, so the dependents check reads every still-running service with its description and its `stillRunningError` in one `startedMu` section (the Start method's step first, then the kinds by name), with no scope lookup; such a service is a reason to skip its dependents like a step the run skipped, whose own record wins when both exist. The check reads the set live, at each batch (see D12), so a dependency whose abandoned call returned nil since an earlier batch is recorded (the late mark records before it clears the abandoned entry) and its dependents start. The dependency graph also follows an export to its source (`dependencyNeighbors`), so an edge declared with `DeclareDependency` to an export that nothing resolved yet orders start and reaches a skipped source; a `DependsOn` edge already did, since it builds the export with its dependent (group 32.4, a defect that predates this change). Cycle detection reads the same neighbours, so such an edge whose export's source depends back on the dependent is now rejected with `ErrCircularDependency`, and a back edge added later by an override makes Start fail with a cycle. The shutdown export pass reads DAG edges only, so it makes the dependents of each export of the pass dependents of the export's source in the pass too (`addExportSources`, repeated to a fixpoint so a chain of exports passes them down to the last source) and the same edge orders shutdown too (32.5). The export itself is not made a dependent of its source: an export that nothing resolved and nothing depends on then shuts its source down in the first round as before, instead of a round later behind unrelated slow services (32.9; a resolved export keeps its DAG edge and the round it always waited); recording the export→source edge in the DAG at `DeclareDependency` instead was rejected, since Explain would list it and it would cover that one path only.
- *Abandonment:* the timer callback adds the step key under `startedMu` before it cancels the step's context (D4).
- *After root Start (review F3):* when root Start is the run that abandoned the step, Start fails and the container stays in its failed start phase: Refresh and Scope.Start return `ErrNotStarted` and Start returns `ErrAlreadyStarted`, as for any failed Start. The late outcome is still recorded or logged, and Shutdown is the way on. The `StartTimeout` godoc says so.
- *Late outcome:* the step goroutine handles it after the user call ends and it sees the abandoned flag. It takes `lifecycleMu` (outer) then `startedMu` (inner, the leaf lock, so the order is safe).
  - Nil return: the step is recorded only if `scopeHolds` still holds the wrapper, `!closingInLine(scope)` and the root is not closing (`closePhase == closeOpen`), then re-checked (see *Record, then re-check* below). Triage E proved the root check missing: `closingInLine` counts only child scope shutdowns, so a late nil return during root Shutdown was recorded until forget removed it.
  - In every case: the step key is deleted from `abandoned`.
  Because a shutdown marks the scope closing under `lifecycleMu` before it removes services, a late mark either happens before the closing mark (and the later `forget` clears it), or it sees closing and is skipped. `forget` also deletes the wrapper's `abandoned` entry, so a removed service leaves nothing behind.
- *Record, then re-check (review F2, also the pre-existing inline path):* removers (`removeService`, an override in `registerLocked`, `shutdownTaken` for `ShutdownNamed` and root Shutdown) remove the wrapper under the scope lock and only then call `forget`, without `lifecycleMu`. So `closingInLine` covers only child-scope shutdowns. Every start record (`startCandidate` and `runStage` on a nil return, and `finishAbandoned`) is therefore made by one helper, `recordIfHeld(step)`: record under `startedMu`, then check `scopeHolds`, and undo the record (under `startedMu`) if the wrapper is gone. Because every removal happens before its `forget`, either the re-check sees the removal and undoes the record, or the removal comes after the re-check and its `forget` clears the record. The scope lock is never taken while holding `startedMu`, so no new lock order appears.
- *Errors and panics:* nothing is recorded, so the next run retries, as for any failure.
- *Logging:* the late outcome is logged per D8, with the candidate's own `*Scope`, so a child-scope service logs `scope=tenant`.
- *Per instance (triage D, I5):* the claim also consults the instance tracker of D14, so an override that registers the same instance, or a clone sharing it, skips a step whose instance has an abandoned call still running.
*Alternatives:* retry an abandoned step immediately (rejected: two concurrent calls on one instance, including the library's own `runRunner`); "handler re-entry is the author's concern" (rejected: the library authors the built-in Runnable handler).

**D6. Parallel start.** Each worker calls `startCandidate`, so each Starter gets its own guard and its own bound. A timeout outcome is an ordinary first error: scheduling stops, and the other running Starters are still awaited, each within its own `StartTimeout`, as the existing "first failure stops scheduling" rule says. So the run returns at most `StartTimeout` after its first failure. A step skipped because its abandoned call still runs (D5) is not a failure: scheduling continues, and its dependents are never scheduled.

**D7. `HookAfterStart` on abandonment.** It is called once by the run, on the run's goroutine, at abandonment, with `elapsed` = the time waited and `err` = the timeout cause (it matches `ErrStartTimeout`). It is not called on the late return, and it is not called at all for a step skipped by the D5 claim or as a dependent of a still-running step, since no `Start` method is called for those. This keeps before and after calls paired one to one, and hook authors never see a call from an unowned goroutine. This is already the natural outcome of D1 + D4, so it is tested together with D4 (tasks group 3).

**D8. Logging on unowned goroutines is panic-safe.** The WARN timer callback (D2) and the late-outcome records (D5) run on goroutines no caller owns. Each record is emitted through `logSafely(func())`, which recovers and drops a handler panic, since there is nobody to re-raise it to. The late-outcome records are:
- WARN "abandoned start step returned": `scope`, `service`, `step`, `kind` (handle only), `elapsed`.
- DEBUG "abandoned start step error": the same attributes plus `error`, emitted only when the call returned an error. Error text stays at Debug, as health-check error text does.
- DEBUG "cancelled start step error" (D12): `scope`, `service`, `step`, `kind` (handle only), `error`, for a step a child scope shutdown cancelled that returned an error; a panic of such a step logs the "panic recovered" records of point "start" plus `step` and `kind`. These are emitted on the run's goroutine, through the ordinary logging path.
- A late panic: the "panic recovered" records of point "start" on the candidate's scope, plus `step` and `kind` (handle only), so every late record names its step the same way (triage E).
Shared attributes come from one `stepAttrs` helper. These records, and the slow warning, can be emitted after Start returned and after the container or the scope closed: the call is still running user code then, and the records say so. The `Logger` godoc lists the new records and states that a handler panic on these goroutines is dropped (triage E: it claimed such panics crash the process).

**D9. Names and zero values.** The new names are `SlowStartThreshold` / `DefaultSlowStartThreshold` and `StartTimeout` / `ErrStartTimeout`. They follow `HealthCheckTimeout` / `DefaultHealthReportCheckTimeout` / `ErrHealthCheckTimeout`. Zero means "default" so that the struct's zero value is the documented default: warning on, timeout off. This is why disabling the warning takes a negative value (see the deviation in the proposal). `Clone` copies `InjectorOpts`, so clones keep both settings.

**D10. Docs: the right and wrong server shapes.** The wrong shape is `Start(ctx) error { return srv.ListenAndServe() }`, which blocks until Shutdown. The right shape: in `Start`, call `new(net.ListenConfig).Listen(ctx, "tcp", addr)` (so bind errors fail Start), with `addr` defaulting to `":http"` when `srv.Addr` is empty, as `ListenAndServe` does (review F6), then `go srv.Serve(ln)`, then return nil. `Shutdown(ctx) error` returns `srv.Shutdown(ctx)`. The runnable example's `Shutdown` never waits for a Serve loop that does not exist. `Start` sets an atomic `serving` flag just before it launches `go srv.Serve(ln)`. When the flag is unset (a failed or skipped `Start`), `Shutdown` returns `srv.Shutdown(ctx)` at once. Otherwise it also waits for the loop to end, in a `select` on `ctx.Done()`. So it returns whatever context it gets, including the context of `root.Shutdown()`, which has no deadline. If an abandoned `Start` sets the flag after `Shutdown` read it, `Serve` returns `http.ErrServerClosed` at once, because `srv.Shutdown` already ran, so nothing leaks. (Review F1. Verification V1: the first fix, a `served` channel made in the constructor, still waited until ctx ended, which is forever for `root.Shutdown()` after a failed bind.) A runnable `Example_starterHTTPServer` listens on `127.0.0.1:0`, so it is deterministic and offline. The `Runner` godoc gets the same "must return" note. The `starter.md` snippets live in a compiled snippet file and are pinned by a new `TestDocs_StarterSnippetsCompiled`, which reuses the `docsRegions` machinery of `docs_snippets_test.go`.

**D11. An unexported test seam for interleavings.** Two review findings (F2, F5) are races whose window no public hook reaches. `RootScope` gets an unexported `startSeam` struct of optional callbacks, nil in production and set only by tests in package `doger`: `beforeRecord(step)`, called between the registration check and the record, and `afterStepDone(step)`, called in `awaitStep` between the `select` and the cause decision. A nil check is the only production cost. The seam is not part of the API and is not reachable from other packages.
*Alternative:* stress tests under `-race`. Rejected because they are flaky as a RED test and as a regression guard, and the project requires a reproducing test for a defect.

**D12. A child scope Shutdown cancels the running start steps of its subtree (triage A/C, I1).** Root Shutdown cancels a whole run; a child scope Shutdown waited without cancelling, so it could wait forever on a Start that stops only on its context, or skip a service whose Start kept running. Now every running step's context (D3 inline, D4 awaited) is registered, under `lifecycleMu`, with the scope of its candidate. When `joinClose` marks a scope closing, it cancels the contexts of registered steps whose scope is that scope or a descendant, with a cause matching `ErrShutdown`, then the Shutdown waits for the run as before (`waitForStartingRun`, bounded by its context). The run treats a step of a closing scope as skipped, not failed: its outcome is not recorded (the late-mark rule of D5 already refuses a closing scope), its error does not become the run's error, and the run checks `closingInLine` before each later step so the rest of that subtree is skipped while other scopes continue. A step that ignores the cancellation is abandoned at its StartTimeout as usual (still tracked and logged); without StartTimeout it is awaited, as the bounded wait already allows. Root Shutdown keeps cancelling the whole run. Under a root Shutdown, which also marks the child scopes it shuts down closing, a child step is cancelled with the run and reported like a root step (a `*StartError` naming it, with the timeout wording once abandoned); the skip rule applies only to a child scope's own Shutdown, while the root is open (`scopeShutdownSkipsSteps`, read by `cancelSubtreeSteps` and `registerStep` under `lifecycleMu`; release triage A and E, decisions I1 and I3). `Scope.Start` still returns nil then, but does not run the `HookScopeStarted` hooks when a shutdown of its scope or of an ancestor began after the run claimed its candidates (code review finding 1): `joinClose` records it, under `lifecycleMu`, against the run's roots (`runRoots`, set by `claimCandidates`), and `finishIncremental` reads it. The claim is the boundary because it is where the shutdown protocol starts to wait for and cancel the run (`runScopes`): a shutdown before it is one the run started after, so the approved "A shutdown that completed before Scope.Start claimed the scope" keeps its Started hook; a sticky record, rather than `closingInLine` at the end of the run, also covers a bounded shutdown that gave up waiting and completed before the run returned. A descendant's shutdown is not the scope's own and leaves its hooks running. A bounded child scope Shutdown that gave up waiting removes the scope's services with their DAG edges and detaches the scope, so an export of it reaches no source any more; a dependent outside it whose dependency is skipped only afterwards was started by the sequential path and silently left pending by the parallel one, whose static `requires` still waited for it (code review finding 2, and 40.6 for an edge declared during the run). The dependents check therefore gives such an export a skip reason of its own as the walk reaches it (`dependentsCheck.checkDetachedExport`, `startRun.detachedExportSkip`): the export's source scope as the run claimed it, found among the claimed candidates through `withinSource` (which compares the export's parent and child scope names and also holds for a shut-down scope), is detached when it is no longer the scope the export resolves from. That comparison is by identity (40.14): the export looks its source scope up by name, so a new scope reusing the name would otherwise make a removed source look live. The edges inside that subtree went with its services, so a path from the source to another service there (a plain exported service that invoked a Starter of its scope, 40.10) cannot be followed; the export is taken to depend on the whole subtree, which is safe since the subtree shut down: a dependent of it outside is skipped once any step there was skipped, even one it did not depend on. The reason, and so the dependent's error, is that of a still-running step of the subtree when there is one (its `ErrStartTimeout` error decides, as for a dependent that reaches it), otherwise the removed export itself (`stepSkip.removedFrom`: "dependency `S` (export of scope `c`) was removed by the scope's shutdown", matching `ErrShutdown`), never an unrelated skipped step (40.15; a first version, 40.10, added the subtree's candidates as neighbours, which named one of them). Under an unbounded shutdown, which removes nothing before the run returns, the same dependent starts when its own dependencies did; the godoc of `Scope.ShutdownWithContext`, the container-start spec and the CHANGELOG state the difference. Every other edge is the live graph's, so an edge declared at any time during the run counts. Cost (40.16): once per service a batch's walk reaches, a scope lookup by ID (`scopeByID`, which searches the scope tree through `ChildByID`) and a service lookup, and for an export a pass over the run's candidates; a walk runs only while the run has skipped a step, an abandoned call still runs, or the instance tracker holds one (`newDependentsCheck`), so a run with none of these pays nothing. A first version (40.2) snapshotted every candidate's transitive requirements once built (`startRun.requires`): it missed an edge declared later, by a `StageBeforeStart` handler for example (40.6), and cost a full traversal per candidate on every multi-scope run, skip or not (40.8: up to +74% time and +89% B/op on `BenchmarkRefresh_MultiScope/chain`); it was removed. The parallel scheduler keeps a guard (`startRun.unscheduledError`, through `endParallelStart`): when scheduling ends with no failure while Starters are still pending, it reports the first one outside a shut-down scope as the dependent of the skipped Starter it waits for, and skips one of a shut-down scope silently, so a parallel run never returns nil with a Starter neither started nor reported. Since the walk follows detached exports, no public scenario reaches it any more (only an edge that vanishes mid-run some other way could); `TestEndParallelStart` pins it. Once a bounded shutdown of a scope completed during the run (`scopeClosing.done`, set under `lifecycleMu` by `finishScopeClose`), `closingScope` returns that scope for its later steps (40.7), so the run skips them as it skips the steps of a closing scope instead of calling them on removed services; this applies while root Shutdown has not begun, as the rest of the skip rule does. The `closed` flag would not do (40.11): `shutdownWithContext` sets it before `joinClose`, which is where the shutdown joins the run (it cancels the steps and records the run-root shutdown for the Started hooks), so a step skipped in between would be skipped while `Scope.Start` still ran the Started hooks; a shutdown that has only closed the scope has not begun for the run. The dependents check keeps `scopeClosing` for `closingItself`: a dependent of a scope whose shutdown completed reaches nothing, its services and edges being gone, so `closingScope` could not change the outcome there.
- *Registry.* `RootScope.runSteps` (a set of `*runningStep`: scope, cancel, `cancelled` flag), guarded by `lifecycleMu`. `runStartStep` registers the step's context before the call (`registerStep`) and unregisters it when it stops waiting (`unregisterStep`, which reports whether a scope shutdown cancelled it), so an abandoned call is no longer registered: the timer cancelled its context already. A step that registers while its scope is already closing (the shutdown began during its before hooks) is cancelled at once, as a step after a mid-run root Shutdown runs with a cancelled context. `joinClose` calls `cancelSubtreeSteps` under `lifecycleMu`; cancelling there runs no user code. The cause is `libErrorf("%w: scope `%s` is shutting down", ErrShutdown, name)`.
- *Dependents of a skipped step (verification W1, user decisions 1 and 2).* A step of a closing subtree that the run skipped (by the closing check before its hooks, or cancelled by the shutdown, whatever it returned) or that was abandoned at StartTimeout is not started for its dependents: the run records it in `startRun` with its reason, next to the still-running set of D5 (a step of a closing scope whose abandoned call from an earlier run still runs keeps both reasons, so its dependents report its own `ErrStartTimeout`), and the dependents check skips every candidate that requires it, directly or through others (exports included; once the run skipped anything, or an abandoned call runs, the check walks the dependency graph as it is then, so an edge a kind handler declares after the first skip counts too, and a run that skipped nothing while no abandoned call runs pays only two lock round trips per check. Cost (group 31 final verification): a check batch, `dependentsCheck`, snapshots the run's skips and the still-running services once and memoizes, over the strongly connected components of the graph (Tarjan, so the members of a cycle share what they reach), the best skipped service each service reaches; a dependents check is then a lookup. A batch stays current while the run's skip count, the abandoned set's change count, the DAG's change count (an edge added, a service removed) and the container's registration count (one atomic add per service stored in any scope, by `Scope.storeLocked`: a registration, an override or a replaced default, any of which can change what a `DependsOn` name resolves to) are unchanged, so the sequential loop, a stage and the parallel scheduling passes reuse it until one of them changes, and a check never answers from a graph older than the latest of those changes. Measured by `BenchmarkRefresh_SkippedLeaf` with an unrelated skipped leaf, chain 500, StartParallelism 8: 77s before, 0.29s after, against 0.26s without the skip), with no hooks and no call, sequential, parallel and kind stages alike. A dependent inside a closing subtree is skipped silently. A dependent outside it is skipped and reported as the run's pending error, set at that skip, not at the dependency's: the dependency's own timeout `*StartError` (matching `ErrStartTimeout`) while its abandoned call still runs, otherwise `newStartError(StartOpStart|StartOpHandle, dependent, …, libErrorf("dependency `%s` was not started: %w", dep, scopeShutdownCause(closing)))`, matching `ErrShutdown`. When the dependent reaches several skipped services (the check walks the whole reachable graph, whose neighbour order is not stable), the error comes from a still-running one first, then the first by scope name, service name and scope ID (`compareSkipped`), so it is the same on every run of a container (scope IDs are random, so the last tie-break, between same-named scopes, is stable within a container only). A step that `claim` finds recorded (its abandoned call returned nil since discovery) is not a skip even when its scope began closing: its dependents start. A real failure of the run still wins over a pending error, as in D5. An abandoned step of a closing subtree with no dependent outside it does not fail the run, which keeps "Child shutdown waits for a stuck step up to the start timeout" returning nil. Rationale: a dependency finishes starting before its dependents, and a run that reported nil would claim success for a live service that never started. A candidate the run dropped at discovery because its scope was already closing is not covered: the run never claimed it, as before this change.
- *Logging (decision 3, D8).* A cancelled step that returned an error or panicked is not reported by the run, so `runStartStep` logs it once the call returned, on the run's goroutine: `DEBUG "cancelled start step error"` with `step.attrs()` plus `error`, or the "panic recovered" records of point "start" plus `step` and `kind`. An abandoned call is logged by its late outcome (D5) instead.
*Alternative:* keep waiting and document (rejected by the user: root and child must behave the same). Starting a dependent of a cancelled step (rejected by the user after verification W1: the run reported success, and started a dependent while its dependency's abandoned call still ran).

**D13. Health reports check a service only once its start is complete (triage D, I4).** `eligibleForReport` skipped a not-yet-started Starter but checked a component whose kind handler had not handled it, so an abandoned or stuck Runnable reported healthy. It now also requires every kind of the service that has a handler to have handled it, so a component registered after Ready waits for `Refresh` as a Starter does. A kind without a handler does not block eligibility, so components of a kind that is never handled stay checked as before. Nor does a kind that the last run covering the component passed over (code review finding 4, a user decision that reverses the earlier rule and its approved `first_handler_after_ready` row; refined by 40.5): a run that collects (claims) a component while one of its kinds has no handler records that kind as passed over, so a handler registered later does not demote the started, healthy component, which stays checked until the next `Refresh` or `Scope.Start` attempts the kind. A run attempts a kind, and clears that record, when it collects the component while the kind has a handler, or when it calls the kind's handler for it (a handler given between discovery and its stage); a call that then fails, is abandoned or still runs holds the component back. A first version (40.4) held a component back only for the kinds a run attempted, which also exempted a component registered after Ready that no run had collected yet: it was checked before any `Refresh`, while its `Run` was never called, and its early failure was cached (review 40.5). Exempting only the kinds a run passed over keeps the earlier rule for that component and the user's decision for a handler given later. Forced paths (`HealthCheck()`, single-service functions) still check every service. Implementation (group 34, revised by tasks 40.4 and 40.5): the kinds of a service are those Start would handle, `kindBindings` (its registration's kinds, plus the implicit Runnable binding under `EnableRunnerAutoDetection`; none for a transient or an alias), shared with `newStartCandidate`. The run records passed-over kinds by wrapper in `passedOver`, under `startedMu` next to `handled`: `recordClaimedKinds` after `claimCandidates` adds the bound kinds without a handler and clears those with one, from the handler list read with `kindEntries` (under `kindsMu`, released before `startedMu` is taken, so the two locks never nest), then drops the record of a candidate a remover forgot meanwhile (as `recordIfHeld` does); `markAttempted` in `runStage` clears the kind once its step is claimed; `forget` clears the service (`markHandledLocked` need not: a kind handles a service only through a handler call, which `markAttempted` precedes, and a run never passes over a kind that has a handler; 40.12). `awaitsKindHandler` returns false without a lock for a service bound to no kind (a container without kinds pays nothing more), and otherwise reads the handler list, then the handled and passed-over records under `startedMu`. Consequences: a service with several such kinds waits for every one (one that failed keeps it unknown); a handled record is per kind id, so replacing a kind's handler with `Handle` keeps its components checked; a kind given its first handler after the run that started a component leaves it checked until the next `Refresh` or `Scope.Start`.

**D14. The no-overlap guarantee holds per instance, across overrides and clones (triage D, I5).** The `abandoned` map is keyed by wrapper, so a same-instance override or a clone could call Start again on an instance whose abandoned call still runs. A second, instance-keyed set records instances with an abandoned call running: it is added to with the step's abandoned mark (D4) and removed from by its late outcome (D5). It lives in a small tracker object that `Clone`/`CloneWithOpts` share by pointer with the source, so a container and its clones see each other's running calls. The guarantee is per instance only for an instance that is one shared object and a valid map key: a non-nil pointer to a value of non-zero size, a non-nil channel, or a non-nil unsafe pointer (`trackableInstance`, on `reflect.ValueOf(instance)`, so an interface holding one counts). Every other instance is tracked per registration only, as before, and documented (user decisions, group 33):
  - a struct or other value: two registrations of equal values are copies, not the same object, so they never block each other;
  - a map: shared, but not comparable, so hashing it as a key panics (group 33 verification proved it: a map-kind Starter crashed the next run);
  - a pointer to a zero-size type: distinct allocations may share one address (`a, b := &zeroStarter{}, &zeroStarter{}` gave `a == b`; the Go spec leaves it unspecified, so the test row holds whatever the addresses are and only logs them);
  - a nil pointer or nil channel: all nil pointers of one type are equal.
  A comparable type does not guarantee a hashable value either (a struct with an interface field holding a slice); the first group 33 attempt, `reflect.TypeOf(instance).Comparable()`, missed that. The tracker is the only start state clones share.
- *Defaults (group 33.8).* A default registration that yielded or was superseded holds no instance for the tracker (`serviceDefault.builtInstanceAny` returns none, reading the state without deciding it, as `isHealthchecker`): its own value is never used, so a clone's abandoned call on that value must not skip its dependents. They still wait for the target: resolving a yielded default records a dependency edge to the target, so the dependents walk reaches the target and checks its instance (pinned by `TestStartTimeout_YieldedDefaultNotTracked/target_tracked`). Resolving through `yieldedTo()` in the check was rejected as redundant with that edge.
- *Implementation (group 33, `root_start_instances.go`).* `abandonedInstances` counts abandoned calls by `(instance, stepKey)`, the same step key as the per-wrapper set (nil for the Start method, the kind id for a handler call), so a handler call of kind K on instance X does not block X's Start, and two containers that each abandoned a call of the same step keep it tracked until both end. `RootScope.instances` points to it; `NewWithOpts` creates one and `CloneWithOpts` replaces the clone's with the source's pointer. `markAbandoned` adds to it (inside the timer callback's `startedMu` section, so before the step's context is cancelled), `finishAbandoned` removes from it after the record and the per-wrapper delete, and `claimStep` consults it after the recorded and per-wrapper checks, returning `stillRunningError()` like the per-wrapper case. `forget` does not touch it: an override removes the old wrapper while its call still runs. Lock order: its mutex is a leaf, taken under `startedMu` (of whichever container) or alone, never taking another lock and never running user code, so lifecycleMu → startedMu → instances.mu.
- *Dependents check (group 33, 33.5).* A tracked instance is still running for the dependents check too, so its dependents are skipped in any scope or stage, as for a still-running registration (a dependent in a scope whose `Scope.Start` does not claim the step, or whose own step runs in an earlier stage than the claim, such as a `StageBeforeStart` component of a clone). A check batch snapshots the tracker once (`snapshot`, one lock round trip; nil when empty, so a container with no tracked call pays nothing more). While the snapshot is non-empty, the walk looks up each service it reaches once per batch (`checkInstance`, from `asReached`): it reads the instance the service already holds, without building it (`builtInstanceAny` on eager, lazy and default wrappers; a transient holds none; an alias or an export stands for its target, resolved as for a health check by `healthSource`, at most 64 hops), and when that instance has a tracked step that this container has not recorded for the service (Start first, then kinds by name), the service becomes a reason with that step's `stillRunningError`, naming the holder. A step this container recorded does not count: it is started here, whatever runs elsewhere on its instance. The tracker counts its changes (an atomic, bumped under its mutex at each fill and clear), and `current` compares it, so a reused batch never answers from a snapshot older than a clone's abandonment or late outcome. The walk itself is unchanged: `TestStartTimeout_SkippedLeafWalkCost` reads the graph exactly as often as before (680/783, 1260/1464, 5150/5253, 10200/10404; the parallel tree row reads 1461 in some runs, before and after the change alike).
*Alternative:* document the per-registration guarantee (rejected by the user: production safety).

## Risks / Trade-offs

- [The warning is invisible without a Logger, and zero-config consumers still hang silently] → Logging is off by default by contract. The Starter godoc, the README and the hang section of `starter.md` tell users to set a Logger, or a `StartTimeout`, when diagnosing. A future `HookSlowStart` stays possible.
- [The abandoned goroutine keeps running user code after Start returned, possibly touching a service that Shutdown is releasing] → This is documented on `StartTimeout` and `ErrStartTimeout`. Shutdown still calls the service's Shutdowner, which is the stop path. A late nil return after removal or during a scope shutdown is not recorded (D5).
- [A step returning exactly at the bound races the timer] → The outcome is either started with a live context or abandoned, never both: the call's mutex orders the timer callback and the call's end (D4), and on abandonment the late outcome goes through D5. "A step that returns exactly at the timeout" pins it over 200 runs.
- [Shutdown bounded below StartTimeout] → Root or child Shutdown waits for the running start only within its own context; past it, it proceeds with the ended context and skips the services it reaches (shutdown-context), so a stuck step is never released by its Shutdowner and keeps running until its call returns, exactly as without the option. Documented on `StartTimeout` and pinned by "A Shutdown bounded below the start timeout"; a Start that honours its context returns before that point (D4, D12). A root Shutdown that gives up waiting reaches the child scopes while their steps may still run: those steps are reported as root steps are, not skipped (D12), so the run's error is the same for a step in any scope.
- [A successful Shutdown report while an abandoned Start still runs] → After root Start abandoned a step, nothing is in flight, so Shutdown does not wait for the call: it calls the service's Shutdowner and can report success while the user's Start code still runs. Documented on `StartTimeout` and `ShutdownReport`.
- [The default warning timer on a consumer's fake clock (review F6)] → With a Warn-enabled Logger, each start step arms one timer on the container Clock, which counts toward a fake clock's `BlockUntil`. Documented on `Clock` and `SlowStartThreshold`; `SlowStartThreshold: -1` removes it.
- [Overlap across clones and same-instance overrides] → Resolved by the per-instance tracker shared with clones (D14). It is new state shared between a container and its clones, which otherwise share no start state; justified because they already share the instances. An instance that is not pointer-like is tracked per registration only, documented on `StartTimeout`.
- [Health reports change for Runnables (D13)] → A component whose kind handler has not handled it is now `HealthUnknown` and not checked by reads and rounds. Flagged as a behaviour change in the proposal; Runner's godoc already requires `Run` to return once running, so only a stuck or still-starting Run is affected.
- [Child scope Shutdown cancels running steps (D12)] → Flagged behaviour change of "Child scope shutdown waits for a start that is starting its services": a step so cancelled is skipped, not a run failure, so Refresh and Start runs that cover a closing scope keep succeeding as before.
- [Tests leave a blocked user goroutine and goleak fails] → Every test releases its blocking code (through its Shutdown or a test-owned channel) and waits for the late outcome before returning. Tests run inside `synctest.Test` (or `testWithTimeout` with a fake clock).
- [A RED test hangs instead of failing] → Before the feature exists, a test whose Starter blocks until released makes Start block. Inside `synctest.Test` that shows up as a reported deadlock ("all goroutines are durably blocked"), which is the expected RED. Fake-clock tests use `testWithTimeout`, which fails rather than hangs.
- [The step ctx outlives the step's timeout when the step returns in time] → This is intended (review F3). It ends with the run, exactly as without the option, and reports no deadline, so no code can mistake it for a bounded ctx.
- [A test seam in production code] → Unexported, nil by default, no allocation; documented as test-only (D11).
- [Per-step timer cost on the hot path] → One `Clock.AfterFunc` + `Stop` per step, and only with a Warn-enabled Logger. There is none in the default configuration, so no benchmark is required.

## Public API & Defaults

Additive API only: no exported identifier changes. Four flagged behaviour changes of existing rules: a child scope Shutdown cancels the running start steps of its subtree (D12), `Scope.Start` skips the `HookScopeStarted` hooks when a shutdown of the scope or of an ancestor that began after it collected its services cancels them, where they used to run, possibly after the Closing hooks (D12, task 40.1; scope-lifecycle-hooks), health reads and rounds skip a component its kind handlers have not handled yet (D13), and the per-instance guarantee spans clones (D14).

| Identifier | Kind | Default / meaning |
|---|---|---|
| `InjectorOpts.SlowStartThreshold time.Duration` | field | 0 → `DefaultSlowStartThreshold`. Negative, or at or above a set `StartTimeout` → no warning. Measured on `Clock`. Needs a Warn-enabled `Logger` |
| `DefaultSlowStartThreshold = 10 * time.Second` | const | The default threshold |
| `InjectorOpts.StartTimeout time.Duration` | field | 0 or negative → off (wait for every step, as today). Positive → per-step abandoning bound; an ended run ctx cancels the step's ctx at once and the run waits up to the bound. The step ctx ends at abandonment, when its scope shuts down, or with the run, as without the option, and reports no deadline. The no-overlap guarantee is per instance, across overrides and clones, for a non-nil pointer to a non-zero-size value, a non-nil channel or a non-nil unsafe pointer; any other instance is tracked per registration only (D14) |
| `ErrStartTimeout` | sentinel | `"doger: start timeout"`, added to `libSentinels`. Matched by the `*StartError` of an abandoned step and by the error a run returns after skipping a still-running abandoned step |

Docs changes: the godoc of `StartWithContext`, the four Starter variants, `Runner`, `HookBeforeStart`/`HookAfterStart` (ctx wording, abandonment call), and `InjectorOpts.Clock` (now also measures these two). README Quickstart note, `docs/docs/service-lifecycle/starter.md` (new "A Start that never returns" section), and `docs/docs/container/options.md` (the two fields, plus the new log records in its logging table if it has one).

Override paths: thresholds and timeout via the fields, log destination and level via `Logger`, time source via `Clock`. Abandonment is avoided altogether by honouring ctx or returning promptly.
